# vRPC over HTTP

vRPC is Vine's Rpc wire protocol. It uses HTTP for request and response transport, identifies Skel services and methods in the URL, carries call metadata in `vrpc-*` headers, and encodes parameters, results, and errors as JSON or CBOR.

This page describes the current HTTP binding. It is intended for non-Go client implementations, Portal Rpc entry debugging, and cross-process troubleshooting. Go application code should normally use a client generated by skelc instead of constructing HTTP requests manually.

## Request Target

Each invocation is an HTTP `POST` request:

```text
POST <endpoint>/<service-skel-name>/<method-skel-name>
```

For example, to invoke the `hello` method on `demo.greeting.GreetingService`:

```http title="request.http"
POST /rpc/invoke/demo.greeting.GreetingService/hello HTTP/1.1
```

The service and method path components are case-sensitive Skel names. The host supplies a different endpoint prefix for each entry mode:

- A business application's HTTP Rpc handler is normally mounted at `/rpc/invoke`.
- A Portal Rpc site provides `/invoke` under the site's base path; the complete external path is determined by the Portal entry and site configuration.
- The vRPC transport itself only parses the final `/<service>/<method>` portion and does not interpret the host prefix.

Methods other than `POST` are not valid vRPC invoke requests.

## Request Headers

| Header | Required | Format and purpose |
| --- | --- | --- |
| `accept` | Yes | `application/vrpc+json`, or a value containing `application/vrpc+cbor` when the result contains binary fields. |
| `content-type` | Yes | Request body encoding: `application/vrpc+json` or `application/vrpc+cbor`. |
| `vrpc-trace` | Yes | Trace data in the form `id=<32 lowercase hex chars>,span=<16 lowercase hex chars>`. |
| `vrpc-client` | Yes | Calling application `name`, `version`, and `instanceId`. |
| `vrpc-options` | No | Invocation options; currently only a positive `timeout` is supported. |
| `vrpc-actor` | No | Base64url-encoded Actor JSON, created or forwarded by a trusted entry layer. |
| `vrpc-initiator` | No | Base64url-encoded original caller information propagated by the Vine runtime. |
| `accept-encoding` | No | Portal external responses support `zstd` and `gzip`. |

Typical headers look like this:

```http title="request.http"
accept: application/vrpc+json
content-type: application/vrpc+json
vrpc-trace: id=123e4567e89b12d3a456426614174000,span=1234567890abcdef
vrpc-client: name=demo.client,version=1.2.3,instanceId=123e4567-e89b-12d3-a456-426614174001
vrpc-options: timeout=10s
```

`vrpc-client` has these constraints:

- `name` uses lowercase letters and dots, such as `demo.client`.
- `version` is a semantic version.
- `instanceId` is a UUID.

`timeout` uses Go duration syntax, such as `500ms`, `10s`, or `1m`. When the header is absent, the core transport does not create an additional deadline. Portal rpcgw uses a `30s` default and rejects values above `120s`.

Direct application-to-application transport requires both `id` and `span` in `vrpc-trace`. Portal rpcgw also requires the header, but it allows an external client to send only `id` and adds an entry span.

Do not send the same header in multiple independent field lines. To declare multiple response media types, put them in one comma-separated `accept` value.

## Request Body

A JSON request body is an envelope containing only `params`:

```json title="request.json"
{
  "params": {
    "name": "Vine"
  }
}
```

Fields inside `params` are defined by the target Skel method input. For a method with input, they are decoded and validated against the generated schema. A missing body, missing `params`, field type mismatch, or validation failure produces `INVALID_REQUEST`.

A method with no input arguments uses the same envelope and may send an empty object:

```json title="request.json"
{
  "params": {}
}
```

CBOR uses the same data model, with the envelope and `params` encoded as CBOR. Generated clients select `application/vrpc+cbor` when request arguments contain a binary type; other requests use JSON by default.

## Response Headers and Body

Every decodable vRPC response contains at least:

| Header | Format and purpose |
| --- | --- |
| `content-type` | `application/vrpc+json` or `application/vrpc+cbor`. |
| `vrpc-status` | Vine Rpc status, such as `OK`, `INVALID_REQUEST`, or `NOT_FOUND`. |
| `vrpc-server` | Server application's logical `name`, `version`, and `instanceId`; the logical name excludes the internal `@runtime` suffix. |

A successful response uses `result` and sets `error` to `null`:

```http title="response.http"
HTTP/1.1 200 OK
content-type: application/vrpc+json
vrpc-status: OK
vrpc-server: name=demo.greeting,version=1.2.3,instanceId=123e4567-e89b-12d3-a456-426614174002
```

```json title="response.json"
{
  "result": {
    "message": "Hello, Vine"
  },
  "error": null
}
```

A method with no output returns `"result": null`.

A failed response sets `result` to `null` and uses `error`:

```json title="response.json"
{
  "result": null,
  "error": {
    "code": "NOT_FOUND",
    "message": "user is not found",
    "reason": "",
    "detail": ""
  }
}
```

Clients must use `vrpc-status` and `error.code` to determine the invocation result; they must not rely on the HTTP reason phrase alone. On success, `vrpc-status` must be `OK` and `error` must be empty. On failure, the status and `error.code` must match.

## JSON and CBOR Negotiation

Request and response formats are negotiated separately:

1. `content-type` selects the request body format.
2. `accept` declares response formats supported by the client.
3. The server returns CBOR only when the method output contains a binary type and `accept` includes `application/vrpc+cbor`.
4. Other responses use JSON.

When a result contains a binary type, a generated client sends:

```http title="request.http"
accept: application/vrpc+cbor, application/vrpc+json
```

Media type parameters are allowed, for example `application/vrpc+json; charset=utf-8`. Plain `application/json` and `application/cbor` are not valid vRPC content types.

## HTTP Status Codes

An application's internal vRPC HTTP handler always uses HTTP `200`; business and framework outcomes are carried by `vrpc-status`. This prevents forwarding layers from treating an Rpc error as an HTTP transport failure.

Portal rpcgw is the external HTTP gateway. It preserves `vrpc-status` and also maps it to a conventional HTTP status:

| `vrpc-status` | Portal HTTP status |
| --- | --- |
| `OK` | `200` |
| `INVALID_REQUEST` | `400` |
| `UNAUTHORIZED` | `401` |
| `CLIENT_FORBIDDEN`, `PERMISSION_DENIED`, `ELEVATION_REQUIRED` | `403` |
| `NOT_FOUND` | `404` |
| `VALIDATION_FAILED`, `OPERATION_FAILED` | `422` |
| `SERVICE_UNAVAILABLE` | `503` |
| `GATEWAY_TIMEOUT` | `504` |
| `INTERNAL`, `UNKNOWN`, and other unmapped statuses | `500` |

`SERVER_UNREACHABLE`, `INVOCATION_CANCELLED`, `INVOCATION_TIMEOUT`, `INVOCATION_FAILED`, and `UNEXPECTED_RESPONSE` are local client invocation errors and are never returned as a server `vrpc-status`.

## Additional Portal rpcgw Behavior

Portal adds external HTTP behavior around the vRPC transport:

- It verifies that the site allows the target service, then performs service discovery and forwarding.
- It runs authentication and permission checks according to the site's Actor policy. External clients should not forge `vrpc-actor` or `vrpc-initiator`.
- It adds an entry span when a valid `vrpc-trace` has no span and derives child spans while forwarding.
- It returns `portal-trace-id` so the client can record the request trace id.
- It removes internal `detail` data from forwarded errors before exposing them externally.
- For responses larger than 4 KiB, it selects `zstd` or `gzip` from `accept-encoding`, preferring `zstd`.
- It applies CORS according to the site configuration. A successful `OPTIONS` preflight returns `204`.

A Portal-facing client should therefore record the HTTP status, `vrpc-status`, and `portal-trace-id` together.

## Complete JSON Invocation

This example targets Portal rpcgw. The actual host and site base path depend on Portal configuration.

```bash title="invoke.sh"
curl 'https://api.example.com/invoke/demo.greeting.GreetingService/hello' \
  --request POST \
  --header 'accept: application/vrpc+json' \
  --header 'content-type: application/vrpc+json' \
  --header 'vrpc-trace: id=123e4567e89b12d3a456426614174000,span=1234567890abcdef' \
  --header 'vrpc-client: name=demo.client,version=1.2.3,instanceId=123e4567-e89b-12d3-a456-426614174001' \
  --header 'vrpc-options: timeout=10s' \
  --data '{"params":{"name":"Vine"}}'
```

For Go client, server, and method metadata APIs, see [Rpc API Reference](./rpc.md). For trace and remaining-timeout propagation, see [Trace and Timeout](../framework/trace-timeout.md).
